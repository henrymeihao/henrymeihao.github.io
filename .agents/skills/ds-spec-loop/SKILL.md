# 仓库原生 Spec 闭环

把 Spec 当作分布在仓库各处的权威系统，而不是一份计划文档。保持以下职责的一致性：

- 仓库指令与架构不变量；
- 工作提案与稳定决策的理由；
- 只追加的决策日志，记录决策、推翻和被拒选项的先后顺序；
- 当前文档与公共契约；
- 源码、类型、配置、包拓扑和生成产物；
- 可执行证据，例如单元、集成、回放、快照和端到端测试；
- 仓库检查和 CI，负责程序可判定的事实；
- Git 与变更评审历史，负责时间线。

保持用户指定的任务边界。`只写规格`、`只做验证`、`审查`、`实现`、`简化` 是不同的任务，不要悄悄把一种变成另一种。

在不同仓库中保持严格闭环。名称、路径、命令和机械检查可以适配宿主仓库；但不能削弱“每个非机械变更都创建或更新一份负责它的决策记录”这条规则。

- 创建、接受、否决、替换、合并、退役或归档决策时，读 [decision-record-lifecycle.md](references/decision-record-lifecycle.md)。
- 做出、改变、推翻或否决一个决策时，以及在改动早先决策可能覆盖的路径之前，读 [decision-journal.md](references/decision-journal.md)。
- 当用户修正、评审发现、前提失效、测量结果或实现中的发现改变了已接受方向时，读 [requirement-change.md](references/requirement-change.md)。
- 需要按决策类别开展调查和取证时，读 [decision-classes.md](references/decision-classes.md)。
- 编写验收条件、实现提案或验证完成情况之前，读 [acceptance-and-evidence.md](references/acceptance-and-evidence.md)。
- 做删除、合并、替换或清理工作时，读 [simplification.md](references/simplification.md)。
- 新增或重组仓库指令、当前文档、reference、生成文档或历史记录时，读 [documentation-discipline.md](references/documentation-discipline.md)。
- 仓库没有同等规范、或想把这个闭环作为长期规则时，读 [adoption.md](references/adoption.md)。

## 先重建仓库权威

1. 先读根部仓库指令，再读管辖目标子树的每个更具体的指令文件。
2. 重建用户要求的结果、明确的非目标，以及尚未确定的产品或架构选择。当缺失的选择会实质影响结果时，先询问再冻结方向。
3. 梳理相关的工作提案、稳定决策、当前文档、公共契约、源码入口、真实组装路径、测试、生成产物和仓库检查。
4. 在创建任何东西之前，先搜索已有的 Spec、RFC、提案、design doc、ADR 和决策记录规范。复用仓库的命名与生命周期。
5. 找到已经负责该决策的记录。更新它，而不是创建平行记录。
6. 给每个可变事实指定唯一的规范归属。其他文件可以摘要或链接，但不能成为独立的详细副本。
7. 把历史记录和 Git 历史当作背景，而不是当前权威。决策日志是例外：读一读你将要改动的路径对应的条目，它们记录了哪些做法已经试过并被拒绝。
8. 在未解决的矛盾之上继续工作之前，先说明矛盾。优先采信仓库的直接证据，而不是过时的计划或 issue 描述。

不要从偏好的实现出发。先陈述一个即使去掉偏好方案也依然成立的问题。

## 覆盖每个非机械变更

只要工作改变了行为、架构、跨文件或跨包共享的契约、工具链/流程、测试策略、持久化/磁盘/线上传输/配置格式，或任何维护者可能重新审视的决策，就要在同一个 PR 或有界变更中创建或更新一份负责它的决策记录。

只有不改变行为、契约、结构、流程、测试策略、持久格式或理由的纯机械或局部编辑可以豁免。不要用工作量、diff 大小、耗时或文件数量作为判断标准。

同一次变更中，还要为每个决策事件追加一条决策日志：有真实取舍的选择、方向变化、推翻或否决。条目写下后不再修改。读 [decision-journal.md](references/decision-journal.md)。

使用宿主仓库既有的决策分类。如果没有，从 [decision-classes.md](references/decision-classes.md) 中选择一个主要类别。分类用于识别决策和可能的失败面，不要求特定的目录结构。

创建新记录之前，先证明没有任何在用记录已经负责该决策。已有归属时，只有当问题可以被独立重新审视、并拥有自己真实的替代方案、后果或稳定契约时，才另建记录。当没有记录或等价契约产物负责某个非机械修正时，创建一个范围狭窄的 bug 修复归属记录。改动了某个文件、模块、实现阶段、测试层次、后续修复或发布步骤，并不自动构成单独的决策。

## 确立负责的提案或决策

对规模较大的后续工作，先创建或修复工作提案再实现。记录：

- 与解决方案无关的问题；
- 拟采用的方向和受影响的归属边界；
- 真实的替代方案及其落选原因；
- 可观察的验收条件；
- 风险、权衡和有意放弃的能力。

对同一次有界变更中已经做出的小决策，在仓库规范允许时可以直接创建或更新稳定决策记录。不要把未完成的工作描述成当前行为。

每个决策只保留一个归属记录。只有决策需要拓扑、协议、schema、不变量、迁移或兼容性细节时才添加专门的技术章节。不要为了满足模板而编造替代方案；要么调查清楚，要么说明证据不可得。

当结果在经验上未知时，不要预先编造最终决策。记录问题、候选方向、观察方法、验收边界和停止条件；执行有界实验；再根据观察结果撰写稳定决策。

## 处理需求变化和新发现

在修正或发现之后继续工作之前，读 [requirement-change.md](references/requirement-change.md) 并核对差异。

- 在同一个未完成的 PR 或变更栈内，直接修订活跃提案，而不是建立永久的替换链；同时为每次被接受的方向变化追加一条日志。提案显示当前方向，日志保留先后顺序。
- 识别哪些结果和验收条件保留、变化或撤回。
- 把现有代码、测试和文档归类为保留、修订、删除或历史。
- 在接受新的外部依赖、经常性成本、隐私暴露、兼容性损失、产品方向或其他仓库政策未授权的重大权衡之前，先询问决策负责人。
- 稳定决策交付之后，创建新的替换决策、互相链接并追加一条日志；绝不把历史改写得像早先的决策从未存在过。

## 让验收绑定直接证据

对每条验收陈述，明确：

1. 什么可观察的行为或缺失能使它成立；
2. 它可能在哪一层失败；
3. 什么直接证据可以证伪它；
4. 获取该证据所用的确切仓库原生命令、检查方式或运行时路径。

让证据匹配失败面：

- 局部逻辑与不变量 → 聚焦的单元测试；
- 包、服务、加载器或运行时组装 → 集成或组装测试；
- 持久化、恢复或事件重建 → 回放/恢复测试；
- 用户或模型可见的行为 → 真实可运行的产品路径和稳定的输出证据；
- 外部服务行为 → 有访问权限时用真实端到端证据，否则明确声明未验证边界；
- 删除 → 反向搜索，加上源码、导出项、注册、清单、文档、测试和持久格式中的缺失确认；
- 文档或生成 reference 的承诺 → 仓库自身的同步检查；
- 依赖方向 → 清单、import 或拓扑检查。

静态源码检查是关于源码的证据，不是运行时行为的证明。格式检查通过只证明被编码的格式规则，不证明语义一致。

使用覆盖变更主张的最小直接证据集。不要仅仅为了让变更显得严谨而添加校验器、基准测试、回放系统、快照框架或合成评估。只有当一条重要的、机器可判定的规则没有现成负责者且容易漂移时，才添加确定性自动化。

## 改动完整的消费者路径

沿仓库真实的组装路径实现，而不是只改叶子模块。追踪适用的链路：

```text
公共契约 → 实现/提供方 → 注册/组装
→ 消费者 → 持久化 → 用户/模型可见行为
```

并非每个仓库都有全部层次。只追踪实际存在的层。

在同一个 PR 或有界变更中，更新每个所辖事实发生变化的权威文件：

- 源码与公共契约；
- 相关测试、fixture、快照和生成产物；
- 当前的架构、包、API 或用户文档；
- 负责的提案或决策；
- 当持久化的工作流程本身变化时，更新仓库指令或检查。

让补丁限定在该决策范围内。无关的发现另行记录，不要把顺手的重构混入变更。

收敛单位是 PR 或有界变更栈，而不是每个中间提交。检查点提交可以分别隔离实现、评审修复、测量或生命周期改写，只要完整变更在交付前收敛一致。

## 面向真实消费者做复查

声称完成之前：

1. 先不看实现，重读用户请求和负责的提案。
2. 用直接证据核对每条验收条件。
3. 对用户或模型可见的行为，至少追踪一条真实组装后的执行路径。
4. 检查反向保证：什么必须不再存在、不再发生、不再可达。
5. 从调用方、用户/模型、运维者和未来维护者的视角审查。
6. 在本地只跑窄而相关的检查；无关的完整矩阵交给既有 CI，除非用户要求或变更本身覆盖全仓库。
7. 汇报实际执行的命令、有意义的结果、跳过的检查和剩余不确定性。“通过”只用于实际执行过的检查。

## 收敛生命周期与当前事实

实现与证据一致后，先确认日志里已经保存了这次改写即将删掉的每个方向变化、被拒备选和触发原文，再按仓库规范把工作提案改写为稳定决策：

- 当一个文件同时承载两个阶段时，改写它的标题和语义章节；绝不只改状态词；
- 把面向未来的提案措辞替换为实际交付的决策；
- 把验收和风险折算为现在时的后果与验证；
- 更新路径、名称、默认值、契约等事实性内容；
- 保留该决策胜出的原因和它放弃的东西。

如果提案被否决，只在该理由还能防止一个可能重复的错误时，保留被评估的提案和简要的否决原因。

替换是决策之间的关系，不是必需的状态或目录。稳定替换要新建互相链接的记录。局部替换时两份记录都保持有效，并注明各自负责的条款。只有当前归属记录保留了旧记录每一项独有的理由、替代方案、后果、验证义务、覆盖缺口、重新引入条件和入站链接之后，才完全合并、退役或归档旧记录。

最后检查：当前文档描述当前行为，稳定决策描述当前理由，测试钉住可观察的承诺，工作提案不会被误读为已完成。

## 汇报结果

先说现在什么已经成立。然后说明：

- 负责的提案或决策及其生命周期变化；
- 追加的日志条目，或为什么不需要；
- 这次工作是更新了既有归属记录，还是有理由新建了记录；
- 需求差异及批准它的权限来源（如有）；
- 发生变化的行为面和权威文件；
- 验收证据和实际运行的命令；
- 明确的缺口、阻塞项，或有意停留在提案阶段的工作。

不要仅仅因为文档存在或某个检查器返回零就宣称工作完成。

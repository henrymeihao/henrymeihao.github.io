# 闭环内的需求变化

当用户修正、评审发现、前提失效、测量结果或实现中的发现改变了已接受方向时，使用本协议。把核对过程放在当前的工作提案或任务状态中；不要建立第二套永久的工作规格系统。

## 给变化分类

| 类型 | 含义 | 归属方动作 |
|---|---|---|
| 澄清 | 措辞变得更精确，但不改变结果、约束、验收或决策 | 更新措辞；不制造历史 |
| 活跃修订 | 未完成的变更改变了范围、提案或验收 | 修订同一个工作归属记录 |
| 证据驱动的细化 | 观察到的证据解决了一个未知项，但不替换核心决策 | 更新提案、证据映射和实现 |
| 稳定反转 | 交付后替换某个 Current 决策或其理由 | 创建新的交叉链接决策 |
| 独立决策 | 新需求有自己的问题、替代方案、后果和反转边界 | 创建单独的归属记录 |
| 改变权限的权衡 | 新成本、隐私暴露、兼容性损失、产品方向或重大架构选择 | 询问决策权限方 |

分界标准是决策的稳定性，不是提交次数、耗时或代码量。

除澄清外，每种类型都要追加一条决策日志。实时修订原地更新提案；日志条目让更早的方向仍然可读。见 [decision-journal.md](decision-journal.md)。

## 核对差异

在工作提案或任务状态中使用一张紧凑表格：

| 项目 | 之前接受的状态 | 新接受的状态 | 处置 |
|---|---|---|---|
| 结果与非目标 | 早先意图 | 当前意图 | 保留 / 替换 / 撤回 / 新增 |
| 约束 | 早先约束 | 当前约束 | 保留 / 替换 / 撤回 / 新增 |
| 验收 | 早先的可观察主张 | 替代项或无 | 保留 / 替换 / 撤回 / 新增 |
| 替代方案与理由 | 早先权衡 | 当前权衡 | 有效 / 已失效 / 新近相关 |
| 源码与契约 | 当前实现 | 要求的方向 | 保留 / 修订 / 删除 |
| 测试与证据 | 当前证明 | 要求的证明 | 保留 / 修订 / 删除 |
| 当前文档/生成产物 | 当前事实 | 要求的事实 | 保留 / 修订 / 删除 |
| 权限 | 已有授权 | 新授权 | 已授权 / 需询问 |

不要把已撤回的验收保留为当前事实。

## 只在涉及重大权限时询问

当方向在用户请求或仓库政策中已明确、且不引入未经批准的重大权衡时，直接继续。

接受以下内容之前先询问：

- 产品范围或公开定位的变化；
- 外部服务、凭证、付费或经常性成本；
- 隐私、安全、数据传输或权限暴露；
- 兼容性损失、迁移负担或不可逆删除；
- 存在真实竞争选项的新架构或归属边界。

展示冲突点、受影响的验收、最小的自洽变更、被放弃的能力，以及需要做出的确切选择。不要让用户裁决常规实现细节。

## 重新收敛

接受新方向之后：

- 先更新工作归属记录，再继续实现；
- 修复每个因此产生分歧的当前权威文件；
- 删除已失效的实现、测试、生成条目、注册和文档；
- 只重跑被差异影响的证据；
- 汇报已撤回的验收和被删除的工作；
- 为被接受的变更追加一条日志，引用触发原文并写明放弃了什么；
- 只在越过稳定决策边界后才使用替换记录。

如果修订后的变更在同一轮内交付，且宿主用一个文件承载 Working 和 Current 两个阶段，就把该文件改写为当前事实：Proposal 改为 Decision，Acceptance 和 Risks 替换为现在时的 Consequences 和 Verification，标题仍称其为提案时一并更新。绝不通过只改状态词把工作标记为已完成。

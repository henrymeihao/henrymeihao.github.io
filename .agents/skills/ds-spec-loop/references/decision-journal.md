# 决策日志

决策日志是只追加的决策事件记录。需要它，是因为其他产物都是有意被改写的：当前文档和稳定决策随代码修改，提案交付时被改写成现在时。代码从 A 改到 B 再改回 A，留下的 Git diff 会互相抵消，下一个读者（人或 agent）什么也看不到。日志保留的就是这段顺序。

当前真相和决策历史的更新规则相反。当前文档、契约和稳定决策过时就覆盖；日志条目永远不覆盖。

## 条目记录什么

每个决策事件一条：有真实取舍的选择、方向变化、推翻、或否决。记录：

- **时间**，以及宿主仓库使用时的任务或卡片号；
- **类型**：`decision`（决定）、`revision`（进行中的工作改变了方向）、`reversal`（撤销之前的选择）、`rejection`（评估过某个候选并拒绝）；
- 决策涉及的**路径**，按当时的样子记；
- 与旧条目的**关系**：`supersedes`、`reverts`、`relates`；
- **触发**：原始证据，如用户的原话、评审发现、测量结果或报错。引用原文，不要转述成"同意"；
- **决定**：选了什么，影响到哪；
- **放弃的备选**以及各自输在哪。没有真实备选就写"无"；
- **后果**：放弃的能力、已知风险，以及应当回头重新评估的条件。

条目可以只有几行。如果说不出放弃了什么，多半说明还没有真正做过选择。

## 规则

1. **只追加。** 条目写下后不再修改或删除。写错或过时，用一条引用它的新条目回应。
2. **在决策发生时写。** 事后写的条目容易变成对结果的辩护，而不是对触发的记录。条目与它解释的代码放进同一次变更提交。
3. **每次被接受的方向变化一条。** 同一个未完成的 PR 内改了主意，也要写独立条目，尽管工作提案是原地修订的。提案显示现在到了哪里，日志显示是怎么到的。
4. **机械编辑和纯澄清不写。** 错别字、格式化、不改行为的重命名，以及不改变结果、约束或验收的措辞调整，都不进日志。
5. **不复制当前事实。** 现状链接到负责它的文档或契约。日志说的是为什么、何时，不是今天怎么运转。
6. **路径按当时记录。** 以后改名，不回头改旧条目。
7. **通过 Git 把条目和提交关联。** 新增条目文件的那个提交就是它的提交。不要存提交号，squash 或 rebase 后它会变。

## 怎么读

改一个路径之前，先找出提到它的条目，从最新的读起，尤其是 `reversal` 和 `rejection`。没有被后来条目 `supersedes` 或 `reverts` 的条目仍然有效。如果眼前要做的事正好是被否决的备选，先读它的触发和后果，只有这些条件变了才继续，并在新条目里写明。

先按路径搜索，只读搜索返回的条目，不要把整份日志都加载进来。

## 与其他产物的关系

| 产物 | 关系 |
|---|---|
| 工作提案 | 工作未完成时原地修订；每次被接受的方向变化同时追加一条日志 |
| 稳定决策 / 当前文档 | 交付时改写为现在时；日志保留被改写删掉的内容 |
| 已发布决策的替换 | 仍然是新建的、互相链接的决策记录；日志同时追加一条指向它的 `reversal` 或 `decision` 条目 |
| Git 历史 | 日志不取代它；Git 记录改了什么，日志记录为什么、拒绝了什么 |
| 任务会话采集 | 可以作为条目的来源；除非它在后来者能搜到的地方保留了决策级别的内容，否则不能替代日志 |

## 强制

不可修改和是否存在是机器可判定的，宿主可以检查：拒绝修改或删除已提交的条目；变更涉及宿主标记为决策相关的路径时，要求带条目。不要自动化触发证据、备选和选择本身的质量。在这类检查出现之前，汇报时要说明这条规则靠约定。

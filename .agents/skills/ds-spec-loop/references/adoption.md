# 在仓库中采用 Spec 闭环

添加文件之前，先把职责映射到宿主仓库。可移植性改变的是名称、路径、命令和机械工具；它不削弱“每个非机械变更都创建或更新一份负责它的决策记录”这条要求。

## 职责映射

1. 读仓库和子树的指令。
2. 找到已有的 Spec、RFC、提案、design doc、ADR 和决策记录。
3. 找到当前的架构、API、包和用户文档。
4. 找到聚焦的测试命令、真实产品路径、生成产物和完整的 CI 检查。
5. 按 [system-of-authority.md](system-of-authority.md) 给每项职责指定一个已有产物。
6. 在创建平行系统之前，先汇报重叠和缺口。

示例：

| 职责 | 可能的宿主形式 |
|---|---|
| 仓库规则 | `AGENTS.md`、`CLAUDE.md`、Copilot instructions |
| 工作提案 | Spec、RFC、提案、design doc |
| 稳定决策 | ADR、决策记录、已实施的设计 |
| 当前文档 | 架构文档、README、API 文档 |
| 决策日志 | `docs/decisions/` 条目、与 ADR 并列的事件日志 |
| 聚焦证据 | `pytest`、`cargo test`、`go test`、`pnpm test`、真实 CLI/UI/API 流程 |
| 完整检查 | GitHub Actions、Makefile、pre-commit、仓库脚本 |

绝不向一个生态系统开出另一个生态系统的命令。从仓库的清单文件、贡献者文档和 CI 中发现命令。

## 先复用，再扩展

- 已有的 ADR/RFC 规范覆盖了某项职责，就用它们。
- 如果 ADR 只覆盖架构，而非机械的 bug、流程或测试决策缺少归属，就提议对现有决策政策做小幅扩展，而不是悄悄让 ADR 超载，或另建一棵无关的目录树。
- 如果工作提案和稳定决策是分开的文件，交付后把它们互相链接，并选定一个当前理由的归属。
- 如果仓库指令与 Skill 冲突，说明冲突。不要悄悄推翻优先级更高的本地政策。

## 最小兜底结构

只有当不存在同等规范时，才提议一个最小的通用结构，例如：

```text
<仓库指令文件>
docs/
├── architecture.md
└── decisions/
    ├── README.md
    ├── yyyy-mm-dd-topic.md
    └── journal/
        └── yyyymmdd-hhmm-slug.md
```

`journal/` 下的条目遵循 [decision-journal.md](decision-journal.md)；宿主没有单独的稳定决策记录时，也可以直接放在 `decisions/` 下。

在每份决策记录中用状态字段表达 proposed、implemented/current 或 rejected 的含义。名称可以按宿主调整。不要预先创建空的分类目录、归档、生成的索引、校验器、翻译或 checksum 清单。

兜底的决策政策 README 要定义：

- 什么时候必须有记录；
- 生命周期语义和宿主的状态词；
- 文件命名约定；
- Working、Current、Declined 各阶段的内容要求；
- 替换与合并；
- 链接风格；
- 需要时的历史保留政策。

## 长期采用

团队级使用时，把严格规则写进仓库指令：

> 每个非机械变更都在同一次有界变更中创建或更新一份负责它的决策记录。复用已有的决策规范，并同步更新当前实现、证据和文档。每个决策事件都追加一条决策日志，提交后绝不修改。

用户也可以只为一次有界变更调用本 Skill。不要引入更轻量的方法，也不要逐任务切换政策。

## 机械检查

先使用仓库已有的检查。只有当一条规则重要、可机器判定、无人覆盖且容易漂移时才添加自动化。合适的候选可能包括：链接解析、状态格式一致性、生成 reference 的同步、被禁止的依赖方向，或删除后的缺失确认。

不要把语义判断自动化，例如问题的质量、替代方案的可信度、用户价值或测试是否充分。

## 渐进式采用

不要重写全部历史决策。把闭环用在下一个非机械变更上，随工作触及顺带修复邻近的在用权威文件，并保留既有历史。渐进式采用改变的是迁移多少历史，而不是未来哪些变更需要归属记录。

# 验收与证据

只有当某个观察结果能够推翻验收条件时，它才是有用的。“实现 X”“补测试”“更新文档”是任务，不是验收条件。

## 编写可观察的验收

好的验收条件明确：

- 行为主体或调用方；
- 起始状态与输入；
- 可观察的行为或缺失；
- 相关时的持久化或兼容性影响；
- 失败行为与反向保证；
- 该主张不再成立的边界。

## 建立证据映射

在工作提案或任务状态中使用一张紧凑表格：

| 验收条件 | 失败面 | 直接证据 | 结果 |
|---|---|---|---|
| 消费者能通过真实组装路径使用该能力 | 注册与组装 | 仓库原生的集成测试 | 记录实际结果 |
| 清理会移除该能力 | 生命周期清理 | dispose/注销观察 | 记录实际结果 |
| 持久化状态能重建行为 | 持久化与投影 | 恢复/回放证据 | 记录实际结果 |
| 被删除的 API 已不存在 | 源码、导出项、文档、目录 | 反向搜索加相关测试 | 记录实际结果 |

写下确切的仓库命令和结果。如果因为缺少凭证、平台、环境或权限而无法运行证据，就声明该边界；较低层的证据只支持它直接观察到的更窄的主张。

## 让证据匹配风险

| 风险 | 主要证据 |
|---|---|
| 解析、转换、局部不变量 | 聚焦的单元测试 |
| 服务/包/运行时组装 | 集成或组装测试 |
| 持久化、恢复、事件顺序 | 恢复或回放测试 |
| 用户/模型可见行为 | 真实应用路径和稳定的输出证据 |
| 外部提供方契约 | 有访问权限时的真实端到端测试 |
| 完全移除 | 覆盖源码、注册、清单、文档、测试和持久格式的反向搜索 |
| 文档结构与链接 | 仓库的文档检查 |
| 生成 reference 的同步 | 重新生成后 diff 干净，或仓库同步检查 |
| 依赖方向 | 清单、import 或拓扑检查 |

一条覆盖面很广的命令不会自动成为每条验收的证据。要说明二者的关联。

使用覆盖变更主张的最窄证据集。质量来自匹配失败面，而不是堆砌测试数量。

## 验证真实消费者路径

叶子测试通过时，功能仍可能不可达。追踪实际存在的层次：

```text
公共契约 → 实现/提供方 → 注册/组装
→ 消费者 → 持久化 → 用户/模型可见行为
```

不要为满足模板而虚构不存在的层。

## 区分机械主张与语义主张

只把确定性的不变量自动化，例如状态格式、链接、生成产物同步、依赖方向或已移除的注册。

不要仅仅因为闭环需要证据就添加通用校验器、基准测试、回放系统、快照框架或合成评估。只有当一条重要的、机器可判定的规则无人覆盖且容易漂移时，才添加确定性自动化。

问题是否重要、替代方案是否真实、验收是否符合用户意图、证据是否针对可能的失败——这些仍由人或 Agent 的评审判定。

## 完成状态的措辞

- “Passed: `<命令>`” 只在成功执行之后使用。
- “Inspected: `<路径>`” 用于静态证据。
- “Not run: requires `<条件>`” 用于无法运行的检查。
- “Inferred from `<证据>`” 只用于明确更窄的推断。

绝不能仅因为记录改了状态或格式检查通过就宣称已实现。

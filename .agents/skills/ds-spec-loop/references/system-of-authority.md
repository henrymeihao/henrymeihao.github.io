# 仓库权威系统

仓库原生的 Spec 分布在回答不同问题的多个产物之中。添加任何东西之前，先复用宿主仓库已有的负责产物。

## 产物职责

| 职责 | 可能的仓库形式 | 负责什么 | 不能变成什么 |
|---|---|---|---|
| 仓库指令 | `AGENTS.md`、`CLAUDE.md`、Copilot instructions、贡献者规则 | 持久规则、命令、架构不变量、上下文地图 | 任务日记或完整设计史 |
| 工作提案 | Spec、RFC、提案、design doc、ADR 草案 | 问题、候选方向、替代方案、验收、风险 | 把未完成的工作宣称为现状 |
| 稳定决策 | ADR、决策记录、已实施的设计、已接受并交付的 RFC | 当前决策为何胜出、替代方案、后果、验证义务 | API 手册、迁移清单、未来计划 |
| 被否决的提案 | 被拒的 RFC、被否决的提案、被拒的决策 | 被评估过的方向及其落选原因 | 当前契约 |
| 决策日志 | `docs/decisions/` 条目、ADR 风格的事件日志 | 每个决策何时、为何被做出、改变、推翻或拒绝 | 当前真相；提交后绝不修改 |
| 历史记录 | 归档、历史、冻结的决策、Git | 过去的理由和时间线 | 当前权威 |
| 当前文档 | 架构文档、README、API/包/用户文档 | 当前拓扑、公共行为、用法、归属 | 提案历史或未实现的愿望 |
| 可执行系统 | 源码、类型、配置、清单、schema | 实际行为、结构、公共契约 | “为什么”的唯一解释 |
| 可执行证据 | 单元/集成/端到端测试、示例、回放、快照、冒烟测试 | 可观察的承诺、回归、反向保证 | 完整的决策理由 |
| 生成的 reference | 生成的 API 文档、目录、schema 文档 | 从源头产物推导出的完整当前清单 | 被手工编辑的平行事实 |
| 机械检查 | 项目脚本、Makefile、pre-commit、CI | 程序可判定的事实 | 产品价值或语义正确性 |
| 输入与交付 | Issue、PR、commit、release note | 任务边界、协作、时间线、交付摘要 | 永久的架构权威 |
| 可复用流程 | 仓库内 Skill、脚本、贡献者指南 | Agent 如何重复一个工作流 | 运行时契约或完成证据 |

## 编辑前先梳理归属

对每个可变事实，确定唯一的规范归属，以及依赖它的其他文件：

| 事实 | 规范归属 | 依赖它的文件 |
|---|---|---|
| 当前调用方行为 | 公共契约和当前文档 | 示例和测试 |
| 设计理由 | 负责的稳定决策 | 其他位置的简短引用 |
| 可观察的承诺 | 验收条件和可执行证据 | 交付摘要 |
| 完整清单 | 源码或生成器 | 生成的 reference |

“更新所有受影响的权威文件”不等于把同样易变的细节复制进每个文件。每个产物只按它负责的问题更新。

## 化解冲突

当产物之间出现矛盾时：

1. 读管辖范围内的仓库指令；
2. 确定公共契约和真实的消费者路径；
3. 运行或检查最贴近的可执行证据；
4. 读在用的负责提案或决策，了解意图和理由；
5. 读取受影响路径的决策日志条目，再检查 Git、被否决的提案和历史记录；
6. 说明矛盾，并在同一次有界变更中修复每个当前权威文件。

代码展示存在什么，但不总能展示意图。决策记录解释意图，但不能证明运行时行为。当前事实要求相关的负责产物达成一致。

## 渐进式仓库上下文

根部指令保持简短、起导航作用。详细规则放在它管辖的子树附近。只加载与任务相关的指令、当前文档、决策、源码和证据。

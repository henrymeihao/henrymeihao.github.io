# 简化是一种 Spec 变更

删除与合并会改变契约、归属和未来的选项。把它们当作决策来处理，而不是日常清扫。

## 确立候选对象

调查：

- 生产环境的消费者和注册情况；
- 公共导出项、类型、配置、清单、目录和生成的 reference；
- 持久化/磁盘/线上传输状态和迁移；
- 验证受支持行为的测试与候选对象的自测试；
- 当前文档和示例；
- 兼容垫片和回退路径；
- 最初的动机和可能的重新引入条件。

只被测试使用的接口也许可以删除，但该测试也可能记录了一个真实契约。要弄清它为什么存在。

## 比较真实的替代方案

至少评估：

- 保留它；
- 缩窄或内化它；
- 用已有的归属方替换它；
- 完全删除它。

优先选择能保留必需行为的最小契约。不要把代码行数或包数量当作唯一的决策指标。

## 明确反向验收

只有当旧能力从每个相关权威文件中消失时，删除才算完成：

- 源码和导出项；
- 注册和消费者查找；
- 清单、目录、生成的 reference、示例和当前文档；
- 持久数据、迁移、线上传输字段和兼容处理，除非有意保留并写入文档；
- 受支持行为的测试。

确认替代行为仍可观察。零结果的搜索只能证明被搜索的那个词，所以要包含命名变体和概念别名。

## 保留决策价值

负责该简化的决策记录：

- 旧接口为何不再值得其成本；
- 完全删除之外的替代方案；
- 放弃的能力和兼容性；
- 存续的归属方；
- 如何确认缺失；
- 重新引入条件。

如果仍有消费者或证据不明确，带着书面理由保留该接口也是有效的结论。

## 保持变更范围窄

不要把无关清理混入删除。净删除的价值在于减少概念和维护负担，而不是把删掉的代码换成投机性的抽象。

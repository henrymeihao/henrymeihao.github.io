# 决策类别

使用宿主仓库既有的分类体系。如果没有，从下面选择一个主要语义类别。类别用于指导调查和取证；它不要求专门目录。

## 功能（Feature）

用于用户、模型或外部调用方可见的新能力。记录：

- 公共行为与归属；
- 该能力如何定义、组装和被消费；
- 相关时的生命周期、清理、持久化、权限和失败行为；
- 真实的替代方案和放弃的能力。

证据通常包括真实组装路径、消费者行为、可见输出和当前公共文档。

## Bug 修复

用于恢复预期契约。记录：

- 可复现的失败或直接缺口；
- 根因而非症状；
- 最小的语义修正；
- 相邻行为为何保持不变；
- 该缺陷是否暴露了缺失的不变量、证据层或流程规则。

优先使用修复前失败、修复后通过的回归证据。当已有记录负责该预期契约时更新它。如果没有决策记录或等价契约产物负责这个非机械修正，创建一个范围狭窄的 bug 修复归属记录；不要让严格闭环失去归属。

## 简化（Simplification）

用于删除行为、代码、包接口、兼容性或重复归属，且不新增能力。记录：

- 移除了什么复杂性或重复归属；
- 存续的归属方；
- 保留的行为；
- 证明旧路径已不存在的反向验收；
- 放弃的能力或兼容性；
- 重新引入条件。

读 [simplification.md](simplification.md)。

## 架构（Architecture）

用于已交付源码的结构：模块/包归属、依赖方向、运行时概念、协议、持久化模型或可替换能力的边界。

把拓扑和不变量写明确。证据通常包括清单/import 或结构检查、公共契约、真实组装、集成行为，以及同步更新的架构文档。

## 流程（Process）

用于围绕已交付源码的工具链、贡献政策、发布、文档工作流或 CI。

区分依靠评审执行的政策和机械化执行。只有当规则重要、可机器判定、无人覆盖且容易漂移时才添加检查。如果自动化没有正当性，就注明评审仍是执行机制。

## 测试（Testing）

用于测试架构、fixture、确定性、快照策略、端到端通道或 CI 分层。记录：

- 现有证据抓不住哪种失败；
- 新证据为何更贴近消费者；
- fixture 和输出如何保持确定性和可评审性；
- 该通道如何进入常规的本地或 CI 执行；
- 基础设施通过时能证明什么、不能证明什么。

可行时，先让该通道在一个已知失败的条件下暴露问题，再恢复到通过状态。

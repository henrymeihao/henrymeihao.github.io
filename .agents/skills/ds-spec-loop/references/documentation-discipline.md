# 文档纪律

分布式 Spec 能运转的前提是：每个事实只有一个归属，且历史材料不会挤占当前事实。

## 把当前事实与理由分开

- 当前拓扑与行为放在架构、API、包和用户文档中。
- 公共契约放在类型、schema、生成的 reference 和当前文档中。
- 为什么、替代方案和后果放在负责的稳定决策中。
- Agent 流程放在仓库指令和 Skill 中。
- 可执行的观察放在测试、示例、快照和运行时检查中。
- 历史记录不进入常规的当前权威检索，除非明确要查历史。决策日志是例外：改代码之前按路径搜索它。
- 决策、推翻和被拒选项的先后顺序放进只追加的决策日志，不放进当前文档。

链接到归属文件，而不是复制详细内容。

## 让决策归属保持足够粗的粒度

创建决策记录之前，先问：

- 是否已有记录负责这个问题或契约？
- 这是否只是后续实现、bug、测试层次或事实性位置的更新？
- 拟建的记录是否有独立的问题、真实的替代方案、后果和反转边界？
- 未来维护者能否在不替换其父决策的情况下有意义地替换这个决策？

改动了文件、阶段或测试面，默认不产生单独记录。

## 交付后清除提案措辞

当前文档和稳定决策描述当下的现实。删除：

- 已完成的清单和迁移计划；
- 写成事实的预测；
- 空的 TODO 和投机性的路线图章节；
- 稳定决策中的提案和验收标题；
- 更适合从源码推导的过时清单；
- 被复制进理由文档的重复 API 参考。

只有当决策日志已经保存了这些内容所承载的历史时，才可以删除它们。推迟的工作以工作提案或精确的当前限制的形式保留。

## 有意识地使用生成的 reference

当源码能可靠产出完整清单时就用生成方式。把源码和生成器当作规范来源，只在有正当理由时添加新鲜度检查，不要把生成输出手工编辑成第二个归属。

## 控制增长

当文档变得难以加载时：

1. 删除重复内容和过时历史；
2. 把细节移到它的归属产物中；
3. 收紧语言，同时保留完整的命题；
4. 按子系统拆分并提供清晰导航；
5. 只有当信息配得上空间时才设置或提高预算。

没有观察到的问题和明确的负责者时，不要创建中心索引、归档机制或数字化预算。

## 保持替代方案真实

替代方案必须在当时的问题和约束下确实可行。不要为满足模板而编造“什么都不做”之类的稻草人方案。

## 评审负责检查无法判定的事

以下问题仍由评审负责：

- 问题的表述是否正确；
- 决策是否服务于真实消费者；
- 替代方案和权衡是否诚实；
- 验收是否符合用户意图；
- 证据是否针对可能的失败；
- 某条历史记录是否仍值得保留。

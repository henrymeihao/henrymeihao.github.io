# 页面层面的 SEO：搜索正文拆到 search.json，补结构化数据、分享图和 sitemap 日期

## 触发
SEO 检查后用户原话："页面层面（我可以直接改）——给我改了提交上去做进去"。检查发现：每页的搜索弹窗内嵌全站正文（文章页约 130KB，关于页约 116KB）；16 篇没有 `summary` 的文章 description 是正文前 110 字硬截，带换行、断在半句，`&` 会被转义两次；没有 JSON-LD、`og:image`、`twitter:card`、sitemap `lastmod`；`/writing/` 标题是「搜索文章」，`/about/` 用的是全站通用描述。

## 决定
- 搜索结果行仍在每页 HTML 里（标题、日期、链接，以及标题+摘要+标签的短文本），首次打开搜索时再取 `/search.json`（按路径给出全文），取到后替换每行的匹配文本。文章页约 130KB → 46KB，关于页约 116KB → 32KB。
- 没写 `summary` 的文章，description 改为：解码实体、压成一行，120 字以内在最后一个句末标点处截断；附近没有句末标点就截到 119 字加「…」。手写 `summary` 也压成一行。
- 文章页加 `article:published_time`、`article:tag` 和 JSON-LD `BlogPosting`（`<` 转义成 `\u003c`，正文不能闭合 `<script>`）。
- 所有页面加 `og:site_name`、`og:image`（`/assets/og-cover.png`，1200×630 的全站封面）和 `twitter:card=summary_large_image`。
- sitemap：文章的 `lastmod` 用发布日期，首页和 `/writing/` 用最新一篇的日期，`/about/` 不写。
- `/writing/` 标题改为「全部文章」，`/writing/` 和 `/about/` 各自有专门的 description。
- `app.js` 加上 `?v=` 版本号，避免缓存期内旧脚本配新页面。

## 放弃的备选
- 搜索结果行也从 JSON 生成：弹窗打开时会先空一下；行本身很小，留在 HTML 里没有体积问题。
- 删掉全文搜索、只搜标题和摘要：会失去已有能力，2026-10-28 的设计明确要求标题和正文都能匹配。
- 每篇文章生成单独的分享图：要额外的构建期渲染依赖，现在用一张全站封面就够了。
- 用 Git 提交时间做 `lastmod`/`dateModified`：构建在提交之前运行，刚改过的文章会拿到上一次的时间；日期不准，搜索引擎会忽略整个字段。
- 首页改为只显示摘要：2026-10-28 的决定要求首页保持全文流，各文章页已有 canonical，重复内容的风险可以接受。

## 后果
- 搜索弹窗刚打开、`search.json` 还没取到时，只能匹配标题、摘要和标签；离线或请求失败时一直是这样，下次打开会重试。
- 文章修改后 sitemap 日期不会变；以后如果加 `updated` 字段，再用它做 `lastmod` 和 `dateModified`。
- 自动截取的 description 依然只是正文开头；想要更好的搜索摘要，就给文章手写 `summary`。
- `search.json` 是新的生成文件，随文章数增长（26 篇约 92KB，未压缩）。

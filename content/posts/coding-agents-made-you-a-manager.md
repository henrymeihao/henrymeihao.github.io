Addy Osmani 在 [《Your coding agents made you a manager》](https://x.com/addyosmani/status/2119332146485891501) 里说，整天和 Coding Agent 一起工作的人，其实已经在做管理：挑任务、写说明、委派、跟进、评估结果，最后决定什么能上线。

我很认同。

过去，程序员主要通过自己编写代码来控制软件的质量。现在，Coding Agent 几分钟就能完成过去需要几个小时的工作，我们越来越多地把代码生产交给 AI，但代码生产得越快，一个矛盾就越明显：**AI 写代码的速度越来越快，人理解代码的速度却没有同比提高。**

这造成了整个社区长期的对 Code Review（以下简称 CR）的痛苦。

Agent 几分钟就能交出几百行代码，评审者却仍然需要花时间读懂这些改动。而评审者不一定熟悉这些改动的背景以及隐含的业务约束，而面对不熟悉的技术栈、上下游系统，在脑海里模拟代码的运行也越发困难。

对大量使用 Coding Agent 的团队来说，CR 正在成为最明显的效率瓶颈之一。

我在解决CR问题的过程中，读了不少社区实践，包括 Claude Code 团队的 [《How the Claude Code team does code review》](https://x.com/addyosmani/article/2114604912520921136)、Cloudflare 的 [AI 代码审查实践](https://blog.cloudflare.com/zh-cn/ai-code-review/)，以及 Addy Osmani 关于 Agentic Engineering 的几篇文章。我逐渐意识到，**CR 只是问题暴露出来的地方，并不是问题本身。**

**我们真正需要解决的是：当代码越来越多地由 Agent 生产，我们应该如何保障代码质量？又凭什么相信 Agent 交付的结果？**

这些实践让我重新理解了软件开发中的质量保障。我也开始把其中的一些方法应用到团队里。

我觉得核心不在于某个 AI Review 工具有多好用，不存在这样的银弹，而是不断塑造更适合的开发全链路：**在 AI 时代，我们应该怎样组织代码生产，以及怎样建立对 Agent 的信任。**

## 一、信任不应该只建立在有人读过代码之上

先回到一个基本问题：我们为什么需要 Code Review？

Claude Code 团队把 CR 的目的归结为两件事：上线前发现并修正缺陷，以及让团队对代码库形成共同理解。

换句话说，读代码只是实现这些目标的一种方式。

过去，代码大部分由人编写，代码生产速度相对有限，让另一名工程师读一遍 diff，是一种成本可以接受的质量保障机制。

但 Agent 改变了这个前提。

代码生产能力大幅提升以后，如果我们仍然要求人逐行理解每一处改动，质量保障的成本就会随着代码量一起增长。

更重要的是，**有人读过代码，并不意味着代码就是正确的。**

人同样可能忽略错误，尤其是面对大量看起来合理、命名规范、测试齐全的 AI 生成代码时。

最近审 CR，我明显感受到这种变化。

好的一面是，代码里低级错误少了很多。大部分提交都有单测，有些还附带 E2E 报告，构建和基础检查通常也能通过。

但新的问题开始突出：

- 代码量太大，按过去的方式逐行读，非常消耗注意力。
- 实现可能是正确的，但写法冗余，绕开了项目已有的公共逻辑。
- 代码可以运行，却未必符合实际的产品需求。
- 评审者不了解决策背景，很难判断为什么要采用某种方案。
- 测试全部通过，也不意味着用户真正关心的行为得到了验证。

这些问题并不能简单地通过「找一个 AI 帮忙读代码」来解决。

因为 AI 同样可能出错，而且它可能审阅的准确度不及人，导致更多bug上线。

我认为这里需要区分两件事。

**信任 Agent，是因为它通常能够完成任务；信任产出，是有足够的证据支持这一次任务确实完成得符合要求。** 一个 Agent 过去写对过一百次，不代表第一百零一次不需要检查。

我们需要的是一套可以持续产生证据的质量保障机制，这个机制能证明，我们可以相信这一次产出。就像我们相信自己的人肉 review 一样。
## 二、不要只让 Agent 写代码，还要让它证明代码是对的

这是我从社区实践里得到的第一个启发。

**质量保障应该发生在整个开发过程中，而不是等代码写完以后才开始。**

Claude Code 团队的大量检查发生在 PR 创建之前。

Agent 写完代码，会运行测试、构建项目、检查实际表现，再由一个没有参与开发过程的新 Agent 审查 diff。

Boris Cherny 曾估计，配备有效验证流程可以让 Claude 的产出质量提高两到三倍。

这背后有一个很简单的逻辑：如果 Agent 没有验证工作的能力，那么「看起来完成了」就容易成为它判断任务结束的标准。

于是，人只能在最后充当测试套件。

### 从代码检查走向行为验证

这也是为什么我越来越重视让 Agent 真正运行代码。

比如，我们团队有一条给文档页新增顶部菜单的 CR。

菜单通过事件总线发出字符串 `'pdf'`，接收方却从事件里读取 `e?.key`。结果是用户选择 PDF，最终导出的却是 PPTX。

这条 CR 并不是没有测试。

新增的测试验证了菜单能力已经注册，但没有真正点击菜单，也没有检查最后导出的文件类型。

如果只看代码结构、命名和已有测试，很容易觉得没有问题。

后来，我让 Agent 顺着真实用户路径检查这个功能，并在 jsdom 里使用真实组件构造了复现。

结果很明确：新菜单的用例失败，旧菜单作为对照通过。

到这里，问题才从「这段代码看起来可能有 Bug」，变成了「在这个具体场景下，新旧菜单产生了不同的行为」。

我觉得这两种结论的可信度完全不同。

**前者是对代码的推测，后者是对软件行为的验证。**

当然，运行测试也不意味着可以完全信任结果。

测试通过究竟意味着什么？它是否覆盖了用户真正关心的行为？Agent 有没有为了通过测试而故意只写乐观的测试？

这些问题仍然需要人来管理。

### 我在团队里的做法

第一步很简单，修改 repo 的 AGENTS.md。

要求 Agent 在开发阶段补充测试，在交付前真正执行单测和 E2E，并明确报告执行结果，而不是只声称「测试应该可以通过」。

第二步，是在拿到 CR 链接以后，再做一次独立检查。

我把这个流程整理成了一个 Skill，让多个上下文相互独立的 Agent 并行检查：

- 一个从需求和验收条件出发，检查功能以及失败路径。
- 一个检查共享调用方、跨模块契约和潜在影响范围。
- 一个检查测试覆盖，并尝试构造最小反例。

这里借鉴了 Claude Code 团队的多 Agent 审查思路，但我做了一点调整。

他们会通过多个 Agent 的判断来过滤误报。我不太愿意把「多数 Agent 认为没问题」直接当成代码没问题的证据。

因为多个 Agent 可能共享同一种错误理解。一个少数意见，反而可能指出最严重的问题。

因此，我尽量让第一轮 Agent 独立检查，不预先告诉它们我的怀疑；对于重要发现，再交给没有提出这个问题的 Agent，重新回到源码和运行结果中验证。

我还要求报告明确区分不同证据：

- 只是阅读代码后推断有问题。
- 已经构造场景，复现了失败。
- 自动化测试通过。
- 已经在真实环境中验证。

它们的证明力不同，应该得到不同的注意力。

## 三、Agent 不知道的事情，往往才是最重要的

第二个问题是上下文。

Cloudflare 在介绍自己的 AI Code Review 系统时，很坦诚地提到了 AI 审查器的局限。

它能够读取 diff 和附近的代码，却不一定理解系统为什么这样设计；可以发现 API 契约发生变化，却不一定知道所有下游调用；也很难仅凭静态 diff 判断某些依赖时序的并发问题。

这些问题有一个共同点：**缺少的信息往往不在这次 PR 里。**

一个有经验的工程师看到某段代码，可能立刻觉得不对劲。

这未必是因为他读代码比 AI 快，而是因为他知道很多代码之外的事情。

比如这个逻辑以前为什么要这样写；某个看起来多余的判断是在防什么问题；团队为什么放弃过另一种实现；一个公共方法还有哪些不容易发现的调用方。

这些东西构成了工程师对代码库的长期理解，也就是我们平时说的经验，或者一种工程嗅觉。

**代码记录了最终的实现，却不一定记录了我们为什么选择这种实现。**

Git 能告诉我们代码发生过什么变化，但那些被否决的方案、历史上踩过的坑、隐藏的业务约束，往往只存在于少数工程师的脑海里。

对 Agent 来说，如果这些信息没有被记录或提供给它，即使能读懂每一行代码，也很难做出同样的判断。

### 把工程嗅觉变成 Agent 能使用的上下文

Claude Code 团队会用 CLAUDE.md 记录技术栈、项目约定和目标，用 REVIEW.md 描述代码审查时需要重点关注的风险。

这给了我很大的启发。但我觉得，还可以更进一步。

**如果我们希望 Agent 具备类似人的工程嗅觉，就需要把过去依赖人记忆的东西，沉淀成它可以查询和使用的上下文。**

为此，我在团队里推进了历史决策记录。

**第一步，是记录决策，而不只是记录代码变化。**

对于存在技术取舍的改动，尽量记录当时的背景、最终选择的方案，以及为什么放弃其他方案。

比如一段看起来可以简化的逻辑，可能是为了兼容某个历史场景而保留的。没有上下文的 Agent 可能直接将其删除；有了决策记录，它就能先了解当时为什么这样设计，再判断这些约束今天是否仍然成立。

我希望记录的不只是「做了什么」，还有「为什么这么做」。

**第二步，是让历史决策重新参与开发和 Review。**

历史决策记录不应该只是一份供人查阅的文档，而应该能在不同阶段被 Agent 使用。

在开发阶段，Coding Agent 可以参考相关决策，理解现有设计的理由，避免重复踩坑，或者无意间破坏历史约束。

在 Review 阶段，Agent 可以结合历史决策与当前 PRD，理解这次改动试图实现什么，再对照实际代码，判断实现是否符合预期。

此外，一些反复修改、容易出问题的地方，也可以通过历史决策被识别出来。经过人工确认后，将这些经验沉淀到 REVIEW.md，调整后续审查的重点。

这里有一个我觉得很有价值的地方：**历史决策记录不仅保存过去的结论，也保留了工程师做出判断的过程。**

从一个 Commit 到另一个 Commit，代码发生了什么变化，背后想解决什么问题，为什么选择这种实现。这些信息既能帮助 Agent 理解代码，也能帮助评审者更快地了解改动背景，而不必完全依赖自己对项目的记忆。

当新的开发和 Review 产生了经过验证的经验，又可以反过来补充历史决策记录。

**过去，我们依赖有经验的工程师记住这些事情。现在，我希望让这些经验成为整个团队和 Agent 都能使用的资产。**

## 四、信任需要积累

前两件事解决的是让 Agent 更有可能做对，以及让我们更容易发现它做错了什么。

但还有一个问题：

**我们怎么知道这套机制真的有效？怎么让签字的人信任这套机制，而不是自己又去人工 review？**

毕竟，我们的最终目标是 **在更少人工介入的情况下，维持甚至提高交付质量。**

我认为至少要关注三件事：

**第一，真正的问题能不能发现。**

尤其是那些过去已经造成过 Bug 或线上事故的改动。

**第二，提出的问题到底有多少是真的。**

大量误报会消耗人的注意力，也会降低开发者对审查系统的信任。

**第三，额外的检查是否真正降低了整体成本。**

如果 Review 时间减少了，但修复 Bug 和处理线上事故的时间增加了，那并没有真正实现提效，只是把成本移到了后面。

要建立的应该是对整套软件交付流程的信任，而不只是对审查器的信任。

可以建立这样一个逐步放权的过程：

最初，Agent 只提供 Review 意见，人仍然完整检查。

之后，在某一类低风险任务中，如果历史评估显示 Agent 能稳定发现关键问题，就让它承担主要检查，人只抽样复核。

再往后，对已具备充分验证证据的任务，可以进一步降低人工介入强度。

一旦出现新的漏报、回归 Bug 或线上事故，就重新提高检查强度。

最终形成：**验证 → 评估 → 积累信任 → 调整人工介入 → 持续验证** 的循环

## 五、人不再需要检查一切，但仍然要承担判断

如果 Agent 能完成编码、运行测试、检查改动，并给出足够的证据，那么人究竟应该做什么？

我觉得这才是「Coding Agent 让你成为管理者」这个比喻最重要的地方。

管理者基本不从事代码编写本身，他们的工作在于知道要完成什么、如何组织工作，以及怎样判断结果是否达到要求。

AI 时代管理 agent 也是如此。

现在，我越来越倾向于把注意力放在几个问题上：

**第一，做出来的东西是否符合需求。**

功能能不能跑只是起点。用户体验是不是符合预期？边界场景有没有考虑？需求本身有没有被理解错？

**第二，实现方式是不是合理。**

有没有复用已有公共逻辑？是不是引入了不必要的抽象？上下文有没有记清楚？三个月以后其他人还能不能修改？

**第三，这件事情究竟该不该这么做。**

是否违背了已有的架构决策？有没有更简单的实现？是否引入了与收益不相称的长期维护成本？

这些问题很难仅靠自动化测试回答。因为测试验证的是实现是否满足某些预先定义的条件，而判断这些条件是否合理，本身就是工程工作的一部分。

### 从审查代码到审查表现

我把这个变化理解为，从审查代码逐渐转变到审查表现。

从为代码负责，转变为为结果负责。

这并不是说不看代码，而是说看代码是一种保障质量的方式，不神话它。面对不同风险、不同类型的任务，应该采用不同的质量保障方式。

低风险、影响范围明确的改动，可以主要检查自动化结果，并快速浏览 diff。

涉及状态流转、异步时序、共享接口的改动，需要沿着真实用户路径和跨模块调用关系进行验证。

涉及权限、数据写入、计费、发布流程等高风险逻辑，仍然要在AI的基础上，花费时间查漏补缺仔细阅读关键实现。

也就是说，**人应该从对所有代码进行同等强度的检查，转向按照风险分配自己的注意力。**

## 六、把个人 Know-how 变成团队的工程基建

前面这些方法，单独看都是一些具体的实践：写 AGENTS.md、补测试、做多 Agent Review、记录历史决策、生成 CR 导读。

我目前把这些个人实践，从个人 Know-how，沉淀为组织化、可复用的质量保障能力。目前我的实践可以分成两层。

### 全局基建

这一层提供多个项目共同需要的能力。

包括可以真实运行代码的沙箱、流水线触发和消息通知、通过需求卡片获取 PRD，以及根据仓库生成和更新接口文档、代码解释的能力。

多 Agent 审查和运行时验证也可以在这一层组织。

它需要能够跨多个 repo 工作，方便前后端工程联合检查，而不是只看某一个仓库里的 diff。

### Repo 级基建

这一层保存项目自己的知识和约束。

包括 AGENTS.md、REVIEW.md、历史决策记录，以及项目特有的测试和验证方式。

我的划分原则是：开发者高频使用、对日常开发有直接帮助的内容，尽量留在 repo 里；不同项目独有的上下文，也由项目自己维护。

两层基建配合起来，最重要的是让 Agent **在正确的阶段，获得正确的上下文，并执行正确的验证。**

需求理解阶段，要知道目标和边界。

编码阶段，要知道工程规范、历史决策和可复用的实现。

验证阶段，要知道验收条件，并能够真正运行代码。

交付阶段，要提供证据、说明风险和未解决的问题。

这也是为什么我认为 AI 时代的代码质量保障，不应该只在 PR 阶段增加一个 AI Reviewer。

纯让 AI 读代码，怎么想怎么不可靠。

## 写在最后

以前，我们倾向于通过自己写代码、理解代码、审查代码来建立信心。

但在 Coding Agent 时代，代码生产速度会越来越快，我们不可能要求人的理解和审查速度与它同步。

这并不意味着应该降低质量要求。

相反，我们需要设计更好的机制，让质量不再依赖某个人是否有时间读完所有代码。让不读代码，也能对功能有信心。

**AI 时代的软件工程，正在从直接控制代码的生产过程，转向设计和管理代码质量的保障机制。**

目前，我把这件事归结为三个方向。

**第一，用验证建立信任。** 让 Agent 不只负责生成代码，还要运行代码、验证行为，并提供可以检查的证据。

**第二，用上下文增加理解。** 把人的历史教训、工程约束和技术决策沉淀下来，让 Agent 不只理解这次改了什么，也尽可能理解为什么要这样做。

**第三，让人的注意力回到判断和责任。** 根据风险决定检查的深度，把更多精力留给产品意图、架构取舍、用户体验，以及最终是否应该交付。

代码依然重要，但是我们控制代码质量的方式正在改变。

信任不是一次性授予的。AI Review 会误报，自动化测试会漏掉问题，历史规则也可能过时。我们需要不断验证这套机制，在它足够可靠的地方减少人工介入，在风险较高的地方重新接管。

我希望未来能够在越来越多的任务上，让 AI 的验证能力达到甚至超过人类 Reviewer 的水平。这是一个可以期待的方向。

回到 Addy Osmani 的话，你不一定想当管理者，但当你开始把代码交给 Agent 去写，同时仍然需要为最终交付的软件负责时，你就已经在做管理了。
